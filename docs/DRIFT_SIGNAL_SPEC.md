# Drift Signal Specification

**Status:** Proposed / implementation-pending  
**Evidence class:** Specification  
**Scope:** Driftwatch

## Purpose

Define a reproducible drift signal before implementing or benchmarking a detector. This document intentionally does **not** claim that Driftwatch currently detects drift with validated accuracy.

## 1. Observation unit

A sample is one evaluation window containing a sequence of agent/workflow observations. Each sample SHOULD include a timestamp, agent/workflow identifier, output representation, and the state variables available to the evaluator.

## 2. Baseline

For a given agent/workflow, construct a reference window from observations collected under a controlled nominal condition. The baseline MUST be frozen before evaluating a perturbation set.

Baseline statistics SHOULD include:

- output/embedding distribution;
- consensus;
- spread;
- truth score, where independently defined;
- information score;
- latency;
- event frequency.

A baseline is experimental data, not a ground-truth statement about correctness.

## 3. Perturbation classes

The benchmark SHOULD contain at least:

1. **Nominal variance** — ordinary stochastic variation with no intended drift.
2. **Gradual drift** — a controlled change introduced over multiple windows.
3. **Abrupt drift** — a step change introduced at a known window.
4. **Recovery** — return toward baseline after perturbation removal.
5. **Near-threshold cases** — perturbations deliberately close to the decision boundary.

Each perturbation MUST carry a ground-truth label generated by the experiment controller, not by the detector under evaluation.

## 4. Candidate drift statistic

The first implementation SHOULD use a transparent multivariate change score rather than a project-specific theoretical construct.

For normalized feature vector x_t and frozen baseline mean μ and scale σ, define:

`z_t = (x_t - μ) / max(σ, ε)`

and the instantaneous score:

`D_t = ||z_t||_2 / sqrt(d)`

where `d` is the number of evaluated features and `ε` prevents division by zero.

A windowed score MAY then be computed as:

`W_t = mean(D_{t-k+1}, ..., D_t)`

The implementation MUST document feature normalization and window length explicitly.

This is a **candidate baseline**, not a claim that this statistic is optimal.

## 5. Decision rule

A detector configuration consists of:

- feature set;
- baseline window;
- evaluation window;
- score function;
- threshold θ;
- persistence requirement p.

A positive detection occurs only when the score exceeds θ for the configured persistence requirement. Thresholds such as `0.009` MUST NOT be treated as calibrated defaults without an experiment establishing them.

## 6. Evaluation metrics

For labeled perturbation windows report:

- precision;
- recall;
- F1;
- false-positive rate on nominal variance;
- detection latency;
- recovery latency;
- performance stratified by perturbation class.

The benchmark MUST report the dataset generation procedure and detector configuration so results are reproducible.

## 7. Required controls

The initial benchmark SHOULD compare the candidate detector against at least one simpler control, such as:

- single-feature thresholding; and/or
- rolling mean deviation.

No superiority claim should be made unless both methods are evaluated on the same generated corpus and operating conditions.

## 8. Adversarial / robustness cases

After the baseline benchmark, evaluate:

- feature noise;
- missing observations;
- correlated feature changes;
- isolated outliers;
- gradual sub-threshold drift;
- perturbation reversal;
- threshold-boundary cases.

## 9. Evidence promotion

The evidence state progresses as:

`SPECIFIED → IMPLEMENTED → UNIT-TESTED → BENCHMARKED → CALIBRATED → REPLICATED`

A stage MUST NOT be inferred from the existence of the previous stage alone.

## 10. Current state

Driftwatch currently has simulation, visualization, memory/event, and observability infrastructure. The repository does not yet establish a validated detector corresponding to this specification. Implementation and benchmarking are therefore future work.
